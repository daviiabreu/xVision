## Introdução

O modelo de detecção de keypoints do campo tem como objetivo identificar, em cada frame de vídeo de uma partida de futebol, os pontos característicos das linhas e marcações do gramado como cantos da área, linha do meio-campo, semicírculos e centro do campo.

A partir desses pontos detectados, será possível calcular uma matriz de homografia que transforma coordenadas de pixel do frame para coordenadas reais em metros sobre o campo (plano 2D), permitindo determinar a posição aproximada de jogadores e da bola, além de calcular distância e ângulo do chute para entrada no modelo de xG.

Os scripts do modelo estão em `src/models/line_tracking/` e são três:

* `dataset.py`: download e organização do dataset
* `train.py`: treinamento do modelo
* `validate.py`: validação do treinamento do modelo

## Primeira abordagem: dataset Roboflow

### Descrição

A primeira abordagem utilizou o dataset público `football-field-detection-f07vi`, disponível no Roboflow Universe no formato `yolov8` pose. O modelo base escolhido foi o **YOLO11x-pose**, com 32 keypoints por frame cobrindo os principais pontos do campo segundo o esquema do Roboflow.

### Configuração

| Parâmetro | Valor |
| --------- | ----- |
| Modelo base | `yolo11x-pose.pt` |
| Dataset | football-field-detection-f07vi v18 (Roboflow) |
| Imagens | 255 treino / 34 validação |
| Keypoints | 32 |
| Épocas | 100 |
| Batch | 14 |
| Resolução | 640 × 640 px |
| GPU | NVIDIA RTX A4000 (16 GB) |

### Resultado

Ao testar o modelo em frames reais de jogos, os keypoints detectados apresentaram comportamento de alucinação: os pontos eram distribuídos aleatoriamente pelo frame, sem correspondência com as linhas reais do campo. As métricas de validação confirmaram o problema:

* **Box mAP50:** ~0.979, detecção do campo como objeto funcionou bem
* **Pose mAP50:** ~0.000, detecção dos keypoints não convergiu

### Hipóteses para o insucesso

### Hipótese 1: dataset muito pequeno

O dataset continha apenas 255 imagens de treino, insuficientes para que um modelo de pose estimation com 32 keypoints consiga generalizar. Modelos YOLO-pose de grande porte tendem a overfitar o bounding box e nunca chegam a aprender a localização dos keypoints com dados tão escassos.

### Hipótese 2: ângulo de câmera único e específico

As imagens do Roboflow foram capturadas predominantemente de um único ângulo de câmera (visão lateral e elevada do campo). Em partidas reais, a câmera muda de posição, zoom e perspectiva constantemente. O modelo, treinado em apenas um tipo de enquadramento, não conseguiu generalizar para os diferentes ângulos presentes nos vídeos de teste.

## Segunda abordagem: dataset SoccerNet

### Descrição

Diante dos problemas identificados, a segunda abordagem combinou duas fontes de dados distintas: as imagens do SoccerNet Calibration 2023, que contém frames de múltiplos jogos, câmeras e perspectivas diferentes, e as labels do Hugging Face (`Adit-jain/Soccana_Keypoint_detection_v1`), que trazem as anotações de keypoints no formato YOLO pose já compatíveis com o treinamento. Essa combinação resolve diretamente as duas hipóteses levantadas na abordagem anterior, o volume de dados e diversidade de ângulos de câmera.

O schema adotado possui 29 keypoints por frame, baseados no padrão SoccerNet, cobrindo cantos de área, semicírculos, linha do meio-campo e centro do campo. As labels estão no formato YOLO pose (.txt), organizadas nas pastas yolo_labels/train/, yolo_labels/valid/ e yolo_labels/test/, e são combinadas com as imagens do SoccerNet pelo script `dataset.py`.

### Configuração

| Parâmetro | Valor |
| --------- | ----- |
| Modelo base | `yolo11n-pose.pt` |
| Dataset | SoccerNet Calibration (via Hugging Face) |
| Imagens | ~16.465 treino / 3.214 validação / 3.142 teste |
| Keypoints | 29 (SoccerNet schema) |
| Épocas | 100 |
| Batch | 16 |
| Resolução | 960 x 540 px |
| GPU | NVIDIA RTX A4000 (16 GB) |

### Resultado

Com o dataset maior e mais diverso, o modelo convergiu nos keypoints: em inferência sobre frames
reais, os pontos do campo passaram a cair sobre a geometria visível na imagem, como mostram a figura
e o vídeo abaixo. A verificação foi visual. Nenhuma métrica de validação deste treino ficou
registrada no repositório, então esta seção não traz número medido, e fechar essa lacuna é o
primeiro item de "Ainda não implementado".

## Como executar

Os scripts estão em `src/models/line_tracking/`. Execute-os na ordem abaixo.

### Pré-requisitos

```bash
cd src/models/line_tracking

pip install ultralytics SoccerNet huggingface_hub
```

### 1. Download do dataset, em `dataset.py`

O script baixa as imagens do SoccerNet Calibration 2023 e as labels do Hugging Face (`Adit-jain/Soccana_Keypoint_detection_v1`), e organiza tudo em um único diretório pronto para o treino.

```bash
# Baixa imagens + labels e organiza em ./dataset
python dataset.py --output ./dataset
```

Se os arquivos já tiverem sido baixados anteriormente, é possível pular os downloads e apenas reorganizar:

```bash
python dataset.py --output ./dataset --skip_images --skip_labels \
    --images_cache ./downloads/images \
    --labels_cache ./downloads/labels
```

O resultado final tem a seguinte estrutura:

```text
dataset/
├── dataset.yaml
├── images/
│   ├── train/
│   ├── valid/
│   └── test/
└── labels/
    ├── train/
    ├── valid/
    └── test/
```

### 2. Treinamento, em `train.py`

```bash
python train.py --data ./dataset/dataset.yaml
```

O melhor modelo é salvo automaticamente em `runs/pose/<name>/weights/best.pt`.

| Parâmetro | Padrão | Descrição |
| --------- | ------ | --------- |
| `--data` | obrigatório | Caminho para o `dataset.yaml` gerado pelo passo anterior |
| `--model` | `yolo11n-pose.pt` | Checkpoint base (ex: `yolo11s-pose.pt`, `yolov8n-pose.pt`) |
| `--epochs` | `100` | Número de épocas de treinamento |
| `--imgsz` | `960` | Resolução de entrada (imagens originais são 960×540) |
| `--batch` | `16` | Tamanho do batch |
| `--name` | `soccernet_keypoints` | Nome do experimento em `runs/pose/` |
| `--device` | auto | `"0"` para GPU 0, `"cpu"` para CPU |

### 3. Validação, em `validate.py`

O script roda inferência sobre uma fonte qualquer, imagem, pasta, vídeo ou webcam , e salva os resultados anotados em `runs/pose/predict*/`. Com `--show_labels`, imprime no terminal o nome e a coordenada de pixel de cada keypoint detectado.

```bash
# Uma imagem
python validate.py --weights ./best.pt --source foto.jpg

# Pasta de imagens
python validate.py --weights ./best.pt --source ./pasta_de_fotos/

# Vídeo
python validate.py --weights ./best.pt --source video.mp4

# Webcam
python validate.py --weights ./best.pt --source 0

# Imprimir keypoints no terminal
python validate.py --weights ./best.pt --source foto.jpg --show_labels
```

| Parâmetro | Padrão | Descrição |
| --------- | ------ | --------- |
| `--weights` | obrigatório | Caminho para o `.pt` treinado |
| `--source` | obrigatório | Imagem, pasta, vídeo ou índice de webcam |
| `--conf` | `0.25` | Confiança mínima para detecção do campo |
| `--kpt_conf` | `0.50` | Confiança mínima para exibir um keypoint no terminal |
| `--imgsz` | `960` | Resolução de inferência |
| `--show_labels` | `False` | Imprime nome e coordenada de cada keypoint |
| `--save_txt` | `False` | Salva keypoints em `.txt` por arquivo processado |
| `--project` | `runs/pose` | Pasta onde salvar os resultados |
| `--name` | `predict` | Nome da subpasta de resultados |

## Conclusão

A primeira abordagem, baseada no dataset do Roboflow com 255 imagens e ângulo de câmera restrito, não foi suficiente para que o modelo aprendesse a localizar os keypoints do campo. A Pose mAP50 permaneceu em zero durante todo o treinamento, com os pontos detectados de forma aleatória nos frames de teste.

A segunda abordagem, utilizando as labels do SoccerNet com mais de 16.000 imagens capturadas em
múltiplos ângulos e perspectivas, resolveu os dois problemas identificados. O modelo convergiu e
passou a detectar os keypoints de forma coerente com a geometria visível do campo. A visualização
superior já calcula a homografia com seu template de campo, mas essa capacidade ainda não chegou ao
pipeline central: `config/pipeline.toml` continua apontando `field` para um stub, como a seção
seguinte detalha.

## Ainda não implementado

O modelo converge e detecta os keypoints, e é isso que esta página mostra. O que ele ainda não faz
é chegar ao pipeline: `config/pipeline.toml` e `config/pipeline.models.toml`, os dois em `src/config/`, declaram `modules.field` como `edge.modules.stubs:StubField`, então nenhum quadro que o sistema
processa hoje carrega homografia, e `pitch_xy` sai nulo.

| O que falta | Como a hipótese será testada na próxima sprint |
| --- | --- |
| O módulo `field` de verdade no lugar do stub | Trocar o `impl` de `modules.field`, rodar `xvision run --all --config config/pipeline.models.toml` de dentro de `src/` e conferir que os quadros passam a carregar `pitch_xy`, que hoje sai nulo |
| O peso publicado onde o time alcança | Ele saiu do Git na MR !56 e virou artefato declarado, mas o manifesto não tem campo `download`: quem clona não consegue obter o arquivo. O teste é `xvision artifact get` resolvendo numa árvore limpa |
| A métrica que depende dele | `occupied_area` é medida em metros de gramado, então ela não existe enquanto não houver homografia. O experimento é declarar a feature e comparar com a coluna do parceiro |
| O erro de reprojeção medido em clipe de partida | Os números desta página vêm do conjunto de validação do SoccerNet. A hipótese é que eles se sustentam no vídeo da Footstats, e o experimento é medir o erro de reprojeção sobre os clipes anotados |
