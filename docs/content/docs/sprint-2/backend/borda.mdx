title: A borda, do clipe ao evento
description: Decode único, a interface que todo módulo cumpre, o grafo que os liga, a plataforma de features e o cache endereçado por conteúdo
---

A borda é a parte do backend que abre o clipe de vídeo e produz o evento de finalização. Ela é a
metade que vai para a Jetson, e a metade de baixo da
[arquitetura do backend](/docs/sprint-2/backend).

O projeto vive em `src/`, e os comandos rodam a partir desse diretório. `config/pipeline.toml` tem
apenas o `shot` real (`edge.modules.shot:BallBreakShot`) e seis stubs;
`config/pipeline.models.toml` ativa cinco das sete espécies (`players`, `ball`, `tracking`, `pose` e
`shot`), enquanto `field` e `identity` permanecem como stubs nas duas configurações. As features
declaradas são `body_part` e `type_of_play`, como resume
[o quadro consolidado da sprint](/docs/sprint-2/o-que-falta). Essa separação é deliberada: permite exercitar a
plataforma de ponta a ponta e medir sua estrutura antes de qualquer modelo. Toda medida de tempo
desta página, por consequência, representa o custo da plataforma, não o custo de inferência.

## Onde se encaixa no fluxo

```text
config/pipeline.toml                        clipe .mp4
  [frames.coarse] [frames.window]                │
  [modules.players] ... [modules.shot]           │
  [features.*]                                   ▼
        │                             ┌──────────────────────┐
        │                             │ frames.provider      │
        │                             │ FrameProvider        │  decode uma vez
        │                             │ + frames.preprocess  │  por quadro cru
        │                             └──────────┬───────────┘
        │                                        │ FrameBatch por PreprocessSpec
        ▼                                        ▼
  ┌──────────────────────────────────────────────────────────┐
  │ graph.order  +  graph.framesets  +  graph.runner          │
  │   ordem topologica sobre needs e sobre a ancora da janela │
  │   ball, field, players, shot        conjunto coarse       │
  │   identity, pose, tracking          conjunto window       │
  │   etapa que levanta vira StageRun com estado e motivo     │
  └───────┬───────────────────────────────────────┬──────────┘
          │ ModuleOutput por especie              │ StageRun por etapa
          ▼                                       │
  ┌────────────────────┐                          │
  │ cache.perception   │  chave = identidade      │
  │ var/cache/         │  do que foi computado    │
  └─────────┬──────────┘                          │
            ▼                                     ▼
  ┌────────────────────┐              ┌────────────────────────┐
  │ runner.assemble    │              │ PipelineMetadata       │
  │ Perception         │              │ versions e timings_ms  │
  └─────────┬──────────┘              └───────────┬────────────┘
            ▼                                     │
  ┌────────────────────┐                          │
  │ features.base      │  quem nao mede sai       │
  │ run_features       │  unavailable com motivo  │
  └─────────┬──────────┘                          │
            └──────────────────┬──────────────────┘
                               ▼
                  ┌────────────────────────────┐
                  │ edge.pipeline.process_clip │
                  │ ShotEvent                  │
                  └────────────────────────────┘
```

## Componentes e responsabilidades

| Componente               | Responsabilidade                                                                                                                                                                   | O que ele **não** faz                                                                                   |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `frames/provider.py`     | abrir o clipe, decodificar cada quadro uma vez e entregar o lote na `PreprocessSpec` pedida                                                                                        | não sabe o que é módulo, feature ou grafo; não limita o próprio pico de memória                         |
| `frames/preprocess.py`   | aplicar cor, enquadramento, tratamentos e normalização sempre na mesma ordem                                                                                                       | não escolhe a spec; não converte coordenada de volta para o quadro original                             |
| `modules/base.py`        | o contrato de três métodos que todo modelo cumpre, mais os tipos que entram e saem                                                                                                 | não escolhe qual implementação roda nem valida o conteúdo dos registros                                 |
| `modules/conformance.py` | a suíte herdável que diz se um adaptador é integrável, sem revisão de ninguém do backend                                                                                           | não testa qualidade de detecção; não roda em vídeo real; não dispensa o dono de importar `edge.modules` |
| `modules/records.py`     | conferir o mínimo que cada espécie promete devolver, por etapa                                                                                                                     | não cobra faixa de valor, calibração de confiança nem JSON Schema                                       |
| `modules/registry.py`    | carregar a implementação declarada em `config/pipeline.toml`, aplicar `frames`, `needs` e `artifact` por cima da spec e repassar todo o resto da entrada como `options` da espécie | não valida o que a implementação devolve; não interpreta nenhuma chave de `options`                     |
| `graph/framesets.py`     | resolver quais índices de quadro cada conjunto nomeado cobre                                                                                                                       | não decodifica; não sabe qual módulo pediu                                                              |
| `graph/order.py`         | ordenar por dependência e recusar ciclo antes de qualquer execução                                                                                                                 | não executa nada                                                                                        |
| `graph/runner.py`        | ordem, execução, degradação declarada, medição de tempo e montagem da `Perception`                                                                                                 | não abre vídeo, não escolhe features e não decide o que vira evento                                     |
| `cache/perception.py`    | gravar e servir saída de módulo endereçada pela identidade da computação                                                                                                           | não decide o que é igual: quem decide é a chave; não tem teto nem expiração                             |
| `artifacts.py`           | descrever o peso por pares de caminho e sha256, e conferir antes de entregar o entrypoint                                                                                          | não carrega o modelo, não converte formato, não escolhe device e não baixa de URL pública               |
| `features/base.py`       | rodar os extractors e transformar impossibilidade de medir em `unavailable` com motivo                                                                                             | não sabe de onde veio a percepção nem quais features existem                                            |
| `features/registry.py`   | resolver a seleção declarada em `[features.*]`                                                                                                                                     | não roda nada e não confere resultado                                                                   |
| `paths.py`               | as três raízes, resolvidas na chamada e relativas à raiz Python em `src/`: `../data/footstats`, `../var` e `config`                                                                | não conhece conceito da API; não guarda fonte de verdade em `var/`                                      |
| `pipeline.py`            | a cola: roda o grafo, lê o instante de contato, chama as features e monta o `ShotEvent`                                                                                            | não abre vídeo, não decide `clip_id`, não lê CSV e não escreve relatório                                |

## Fluxo de dados

Entra um clipe `.mp4` e o arquivo `config/pipeline.toml`. Sai um `ShotEvent` em JSON, validado
contra o schema, mais uma lista de `StageRun` com o estado e o tempo de cada etapa.

A configuração declara os conjuntos de quadros e a implementação de cada espécie. O trecho abaixo
é o arquivo real em uso nesta sprint:

```toml
[frames.coarse]
strategy = "uniform"
fps = 5

[frames.window]
strategy = "around"
anchor   = "shot"
before_s = 1.5
after_s  = 0.5
fps      = "native"

[modules.players]
impl   = "edge.modules.stubs:StubPlayers"
frames = "coarse"

[modules.pose]
impl   = "edge.modules.stubs:StubPose"
frames = "window"
```

Diz primeiro que as sete espécies apontam para `dense` nas duas configurações, que o `window` está declarado e sem ninguém dentro, e que só o `config/pipeline.oracle-janela.toml` o exercita hoje; a frase da assimetria vira condicional ("quando alguma espécie voltar para o `window`").

Cada módulo declara o que consome, e o provider entrega exatamente aquilo:

```python
@dataclass(frozen=True)
class ModuleSpec:
    kind: str            # players, ball, field, tracking, pose, identity, shot
    name: str
    version: str
    frames: str          # qual conjunto de quadros ele consome
    preprocess: PreprocessSpec
    needs: tuple[str, ...] = ()
    batching: Batching = PerFrame()
    artifact: str | None = None


class PerceptionModule(Protocol):
    spec: ModuleSpec

    def load(self) -> None: ...
    def infer(self, batch: FrameBatch, ctx: ModuleInputs) -> ModuleOutput: ...
    def close(self) -> None: ...
```

O `ModuleOutput` traz um conjunto de registros por quadro, e cada espécie promete um mínimo de
chaves: `players` e `ball` devolvem `box` e `confidence`, `tracking` e `identity` devolvem
`track_id`, `pose` devolve `track_id` e `keypoints`, `shot` devolve `frame_index`, e só `field` não tem mínimo cobrado, porque ajuste de homografia sai com erro de reprojeção e não com confiança. A caixa sai
em pixel do quadro original, nunca do tensor pré-processado.

Rodando o grafo sobre a fixture sintética, que tem 30 quadros a 10 fps, o resultado é este:

```text
etapa      conjunto  estado        ms  nome@versao
ball       coarse    ok           3.2  stub-ball@0.1.0
field      coarse    ok           0.1  stub-field@0.1.0
players    coarse    ok           0.1  stub-players@0.1.0
shot       coarse    ok           0.1  stub-shot@0.1.0
identity   window    ok           5.4  stub-identity@0.1.0
pose       window    ok           0.7  stub-pose@0.1.0
tracking   window    ok           0.6  stub-tracking@0.1.0

quadros na percepcao: 26, de 0 a 28
primeiro quadro calibrado: 0, 6 jogadores
bola em metros: (36.0, -9.0)
```

Duas etapas custam uma ordem de grandeza a mais que as outras, e elas são exatamente a primeira
etapa de cada conjunto de quadros: `ball` é a primeira a tocar o `coarse` e `identity` é a primeira
a tocar o `window`. O tempo delas é o decode e o pré-processamento, cobrados de quem chega
primeiro. Em sete execuções seguidas na mesma máquina, `ball` ficou entre 2,9 ms e 3,5 ms,
`identity` entre 4,2 ms e 5,0 ms, e `field`, `players` e `shot` deram 0,1 ms em todas: a razão
entre a primeira etapa do `coarse` e as três seguintes fica perto de trinta. Isso é a medida do
decode único acontecendo, e é também o motivo de nenhum número desta página descrever inferência:
os stubs leem um dicionário.

O mesmo se enxerga contando as chamadas. Os sete módulos pedem 123 pares de quadro e módulo, o
provider prepara 47 tensores distintos e decodifica 26 quadros crus, em 2 idas ao leitor de vídeo.
As duas specs de pré-processamento em uso são as constantes `COARSE` e `FINE` de
`edge.modules.stubs.perception`, e não os conjuntos de quadros de mesmo nome: a `COARSE` responde
por 26 tensores e a `FINE` por 21. Instrumentando etapa por etapa, `ball` faz 1 leitura de 15
quadros crus e prepara 15 tensores, `identity` faz 1 leitura de 11 quadros e prepara 21, e
`tracking` prepara mais 11 sem voltar ao arquivo, porque roda no `window` com a spec `COARSE`.
`field`, `players`, `pose` e `shot` não decodificam nem preparam nada: leem do dicionário em
memória. Medido instrumentando `VideoSource.read` e `frames.preprocess.prepare` numa execução
completa.

O evento que sai é este, com os campos de procedência preenchidos pelo runner:

```json
{
  "schema_version": "1.0",
  "shot_id": "synthetic:18",
  "clip_id": "synthetic",
  "match_id": null,
  "shot_timestamp_s": 1.8,
  "features": [],
  "pipeline": {
    "versions": {
      "ball": "stub-ball@0.1.0",
      "field": "stub-field@0.1.0",
      "players": "stub-players@0.1.0",
      "shot": "stub-shot@0.1.0",
      "identity": "stub-identity@0.1.0",
      "pose": "stub-pose@0.1.0",
      "tracking": "stub-tracking@0.1.0"
    },
    "timings_ms": {
      "ball": 3.773,
      "field": 0.368,

    "host": "laptop",
    "started_at": "2026-08-25T03:09:02.584Z"

```

`features` sai vazio porque `config/pipeline.toml` ainda não declara nenhuma seção
`[features.nome]`. A plataforma existe e nenhuma feature foi escrita: essa é a situação real, e o
evento a declara em vez de esconder.

O mesmo comando sobre um clipe real do parceiro não produz evento nenhum:

```text
a especie 'shot' rodou e nao apontou instante de contato em nenhum quadro
```

O stub de `shot` só aponta contato no quadro 18 do gabarito da fixture. Num clipe de 420 quadros
esse índice não é amostrado, a espécie roda e não devolve registro, e o pipeline recusa produzir
evento em vez de inventar um instante. É a degradação declarada funcionando no caso mais
desconfortável, que é o de hoje.

## Referências

- [OpenCV, classe `VideoCapture`](https://docs.opencv.org/4.x/d8/dfe/classcv_1_1VideoCapture.html), que documenta `CAP_PROP_POS_FRAMES` e `grab`, base da decisão de ler em sequência com limiar.
- [FFmpeg, documentação da opção `-ss`](https://ffmpeg.org/ffmpeg.html), que declara que na maioria dos formatos não é possível buscar exatamente, então a busca cai no ponto anterior e o trecho entre ele e a posição pedida é decodificado e descartado. É a razão de uma busca custar dezenas de milissegundos.
- [PEP 544, Protocols](https://peps.python.org/pep-0544/), que é a base de tipagem estrutural do contrato de três métodos, e o motivo de nenhum módulo precisar herdar do backend.
- [PEP 578, Python Runtime Audit Hooks](https://peps.python.org/pep-0578/), mecanismo usado pelo teste de conformidade que detecta um módulo abrindo vídeo por conta própria.
- [pytest, fixtures](https://docs.pytest.org/en/stable/how-to/fixtures.html), base da suíte de conformidade herdável, em que o dono do modelo só fornece a fixture `module`.
- [TOML v1.0.0](https://toml.io/en/v1.0.0), formato da configuração que seleciona módulos, conjuntos de quadros e features.
- [Python, `importlib.metadata`](https://docs.python.org/3/library/importlib.metadata.html), que sustenta a resolução por entry point do grupo `xvision.modules`, alternativa ao caminho de import literal.
- [TensorFlow, SavedModel](https://www.tensorflow.org/guide/saved_model), que é um diretório com `saved_model.pb` e a pasta `variables/`, e [OpenVINO, formato IR](https://docs.openvino.ai/2025/documentation/openvino-ir-format.html), que é o par `.xml` mais `.bin`: os dois formatos de várias partes que justificam o manifesto de peso aceitar mais de um arquivo.
- [JSON Schema, draft 2020-12](https://json-schema.org/draft/2020-12/release-notes), contrato do evento que a borda produz.
- [NVIDIA, desempenho do DeepStream](https://docs.nvidia.com/metropolis/deepstream/dev-guide/text/DS_Performance.html), que mede o pipeline completo incluindo decodificação e pré-processamento, e sustenta a decisão de medir a etapa inteira e não só a inferência.
- [NVIDIA, utilitário `tegrastats`](https://docs.nvidia.com/jetson/archives/r36.2/DeveloperGuide/AT/JetsonLinuxDevelopmentTools/TegrastatsUtility.html), ferramenta do experimento de memória descrito acima.
