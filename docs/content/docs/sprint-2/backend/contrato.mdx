Esta página descreve `src/contracts`, a área que define o que é um evento de finalização e que não
importa nenhuma outra: `edge`, `cli` e `mlops` a importam direto, e a `api` chega ao evento pelo `edge`. Só o `edge` monta o `ShotEvent`; o `mlops` importa daqui apenas os tipos de percepção, `Clip`, `Box` e `FramePerception`. Ela é o acordo entre quem produz o evento na borda e quem o consome, e é a peça de `contracts` na [arquitetura do backend](/docs/sprint-2/backend).

## Onde se encaixa no fluxo

```text
   quem produz                        o contrato                      quem consome

  edge.modules                 ┌────────────────────────┐        cli
  edge.features  ────────────► │  ShotEvent congelado   │ ─────► var/runs/.../events.jsonl
  edge.pipeline                │  FeatureValue          │
                               │  PipelineMetadata      │        api
                               └────────────┬───────────┘ ─────► lista de Metrica no JSON
                                            │
                                    to_dict │ dict só com escalares JSON
                                            ▼
                               ┌────────────────────────┐        nuvem
                               │  validate_shot_event   │ ─────► transporte ainda não existe
                               │  Draft202012Validator  │
                               └────────────┬───────────┘
                                            │ lê
                               ┌────────────▼───────────┐
                               │  shot_event.v1.json    │
                               │  fonte única do que    │
                               │  o evento pode ser     │
                               └────────────┬───────────┘
                                            │ padrão do shot_id, enum de status
                                            └──► lidos por events.py na importação
```

A seta de baixo é a que sustenta a decisão da fonte única: o mesmo arquivo que o validador consome
também alimenta os tipos Python na hora do import. Ele não é documentação do contrato, ele é o
contrato.

## Componentes e responsabilidades

| Arquivo              | Responsabilidade                                                                                                                                                       | O que ele **não** faz                                                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `shot_event.v1.json` | declara o evento em JSON Schema draft 2020-12: campos obrigatórios, tipos, `additionalProperties: false`, o padrão do `shot_id`, o enum de `status` e o perfil de data | não conhece Python, não valida nada sozinho e não diz nada sobre o conteúdo de `evidence`                                   |
| `schema.py`          | localiza e lê esse arquivo por `importlib.resources`, e expõe `load_schema`, `SCHEMA_VERSION`, `SCHEMA_FILENAME` e `SCHEMA_PATH`                                       | não importa biblioteca de terceiro, não valida e não guarda o schema em cache: cada chamada de `load_schema` relê o arquivo |
| `events.py`          | os tipos congelados `ShotEvent`, `FeatureValue` e `PipelineMetadata`, as invariantes cobradas na construção e a serialização explícita                                 | não importa `jsonschema` e não confere presença de chave: `from_dict` assume payload já validado                            |
| `validation.py`      | valida um dicionário contra o schema e traduz o erro do validador para `SchemaValidationError`                                                                         | não constrói evento e não importa `jsonschema` no topo do módulo                                                            |
| `perception.py`      | os tipos que circulam entre os módulos da borda, como `Clip`, `Box` e `FramePerception`, e que o `mlops` também consome                                                | nunca é serializado no evento, e por isso não tem `to_dict` nem entrada no schema                                           |
| `demo.py`            | monta um evento completo, valida e imprime, servindo de prova ao vivo e de fixture dos testes                                                                          | não abre vídeo e não roda módulo: os valores são de exemplo, não medidos                                                    |

A fronteira mais forte da tabela é a primeira linha da própria área: `contracts` não importa
`edge`, `mlops`, `cli` nem `api`. Isso é cobrado pelo teste de fronteira descrito na
[visão geral](/docs/sprint-2/backend), e é o que permite que qualquer uma das outras
áreas dependa do contrato sem arrastar o resto do sistema junto.

## Fluxo de dados

Entra o resultado do pipeline da borda: a percepção montada quadro a quadro, o instante de contato
apontado pelo módulo `shot`, a lista de `FeatureValue` que os extratores produziram e a procedência
da execução. O `edge.pipeline` junta isso num `ShotEvent`, derivando `shot_id` de `clip_id` mais o
índice do quadro e `shot_timestamp_s` desse índice dividido pelos fps do clipe.

Sai um dicionário só com escalares que o JSON serializa, e daí uma linha por evento. O `cli` grava
`json.dumps(evento.to_dict())` seguido de quebra de linha em `var/runs/.../events.jsonl`, no
formato [JSON Lines](https://jsonlines.org/); o `api` traduz a mesma lista de features para o JSON
que o frontend consome.

O evento abaixo não é exemplo inventado. Ele é a saída de:

```bash
cd src
uv run python -m contracts.demo
```

As listas e objetos aninhados aparecem compactados aqui só para caber na página; o comando imprime
o mesmo conteúdo com um item por linha. Gravado como o `cli` grava, com `json.dumps` e os
separadores padrão, esse evento ocupa 1231 bytes numa linha, medido nesta estação.

As três features existem para mostrar os três estados que o contrato admite. `shot_distance_m` é
número medido, com confiança. `shot_angle_deg` é número medido que a borda não confia, e por isso
carrega `reason` dizendo qual limiar estourou. `gaze_on_ball` é ausência declarada: valor nulo,
confiança nula e o motivo por extenso. O contrato proíbe que o terceiro caso se disfarce dos dois
primeiros, porque `reason` vazio com `status` diferente de `ok` é recusado nos dois lados. Zero
inventado passando por medida é o modo de falha que a área inteira existe para evitar, e a
[página da borda](/docs/sprint-2/backend/borda) descreve como os extratores degradam para chegar
aqui.

O `pipeline` é a procedência: qual módulo rodou, em que versão, quanto tempo cada etapa levou e em
que máquina. Os tempos acima são do `demo`, não de uma execução real.

## Referências

- [Especificação de validação do JSON Schema, draft 2020-12](https://json-schema.org/draft/2020-12/json-schema-validation), que sustenta repetir o `format: date-time` como `pattern`: no draft 2020-12 `format` é anotação, e só vira asserção se a implementação decidir isso.
- [JSON Schema, expressões regulares](https://json-schema.org/understanding-json-schema/reference/regular_expressions), que sustenta o risco do dialeto: o guia diz que a sintaxe é a de ECMA-262 e recomenda restringir-se a um subconjunto porque ela não é suportada por inteiro em todo lugar, enquanto a implementação usada é a do módulo `re`.
- [Documentação do `jsonschema`](https://python-jsonschema.readthedocs.io/en/stable/), a implementação de `Draft202012Validator` usada em `validation.py`.
- [Âncoras `$` e `\Z` no módulo `re`](https://docs.python.org/3/library/re.html), a diferença exata que obriga o tipo a reescrever o padrão de `started_at`: `$` casa também antes de uma quebra de linha final, e `\Z` casa só no fim da string. A documentação atual já chama essa âncora de `\z` e mantém `\Z` como nome de compatibilidade, e o piso do projeto é Python 3.10, onde só `\Z` existe.
- [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339), o formato de data e hora do qual `started_at` adota um perfil estreito.
- [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259), que define chave de objeto JSON como sempre textual, motivo de `evidence` recusar chave que não é string.
- [Documentação de `importlib.resources`](https://docs.python.org/3/library/importlib.resources.html), que sustenta ler o schema como recurso do pacote em vez de caminho do repositório.
- [Configuração de build do Hatch](https://hatch.pypa.io/latest/config/build/), que descreve como o arquivo entra no wheel, propriedade verificada pelo teste que constrói o pacote.
- [Documentação de `dataclasses`](https://docs.python.org/3/library/dataclasses.html) e [de `types.MappingProxyType`](https://docs.python.org/3/library/types.html#types.MappingProxyType), a base do congelamento em profundidade dos tipos.
- [JSON Lines](https://jsonlines.org/), o formato de uma linha por evento em que o `cli` grava a saída.
