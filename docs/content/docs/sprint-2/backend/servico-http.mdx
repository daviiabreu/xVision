O serviço HTTP é a ponte entre o navegador e [a borda](/docs/sprint-2/backend/borda), e a área
`api` da [visão geral do backend](/docs/sprint-2/backend): ele aceita o vídeo, enfileira o
processamento e devolve o resultado por etapa. Na arquitetura de destino essa ponte cruza a rede,
e nesta sprint as duas pontas rodam na mesma máquina.

## Onde se encaixa no fluxo

```text
navegador                    serviço HTTP (src/api)                borda (src/edge)
    │                               │                                    │
    │ POST /v1/videos/upload-url    │                                    │
    ├──────────────────────────────►│ store.criar: id + token de 32 B    │
    │◄──────────────────────────────┤                                    │
    │                               │                                    │
    │ PUT uploadUrl, binário cru    │                                    │
    ├──────────────────────────────►│ middleware confere Content-Length  │
    │                               │ grava por pedaço em var/uploads/   │
    │                               │ probe() abre o cabeçalho do vídeo  │
    │◄── 202 {"status":202,"id":5} ─┤ execution.submeter ► fila de 1 ────► process_clip
    │                               │                                    │
    │ GET /v1/videos/status/5       │                                    │
    ├──────────────────────────────►│ lê var/api/jobs.db                 │
    │◄─ "Em processamento" ─────────┤◄─── store.marcar(Finalizado) ──────┤
    │                               │                                    │
    │ GET /v1/videos/5              │                                    │
    ├──────────────────────────────►│ uma linha por etapa do pipeline    │
    │◄──────────────────────────────┤                                    │
```

O serviço é área de composição, como o `cli`: ele importa `edge` e ninguém o importa de volta.
Essa direção é cobrada por teste, e não confiada à disciplina.

## Componentes e responsabilidades

| Componente | Responsabilidade | O que ele **não** faz |
| --- | --- | --- |
| `api/__init__.py` | rotas, middlewares, ciclo de vida e a tabela de códigos que cada rota declara | não roda pipeline, não escreve SQL e não decide o que é uma feature |
| `api/schemas.py` | a forma do que entra e do que sai, e a regra de tipo de cada métrica | não escolhe status HTTP, não toca no banco e não monta o resultado: quem preenche é `execution.py` |
| `api/store.py` | o estado dos vídeos e das contas, em SQLite, com a máquina de estados dentro | não conhece HTTP e não decide o que fazer com um vídeo interrompido |
| `api/execution.py` | rodar o pipeline fora do ciclo da requisição, com teto de fila, e traduzir o evento da borda em uma linha por etapa | não deixa exceção subir, não sabe quem chamou e não impõe prazo ao desligamento: ele cancela o que não começou e espera o clipe em voo |
| `api/seguranca.py` | traduzir o cabeçalho `Authorization` em `Principal` e cobrar a [posse do vídeo](/docs/sprint-2/backend/autenticacao) | não emite credencial e não guarda segredo |
| `api/auth.py` | assinar sessão, conferir senha com `scrypt` e resumir token de serviço | não fala HTTP e não lê o banco |
| `api/export.py` | escrever `src/api/docs/openapi.json` a partir do app que roda | não edita o contrato à mão |

A fronteira mais importante é a de `store.py`: ele lê os vídeos que uma queda deixou pelo meio e
não faz nada com eles. Quem sabe reprocessar é a camada que tem a fila, então a decisão mora em
quem pode submeter, e não em quem sabe consultar.

## Fluxo de dados

Entra um clipe de vídeo e sai uma lista de etapas do pipeline, uma linha por módulo de percepção.
O que segue é a troca real, capturada contra o serviço rodando sobre a fixture sintética do
repositório (3 s, 30 quadros, 320 por 240, 25 KB), com os identificadores como saíram.

O frontend pede um endereço de envio:

```json
{ "fileName": "synthetic.mp4", "contentType": "video/mp4" }
```

E recebe o identificador e o endereço, já com a versão dentro:

```json
{ "id": 5, "uploadUrl": "http://127.0.0.1:8099/v1/videos/upload/gjhFiaaIccwFyLBkPXPq..." }
```

O `PUT` naquele endereço leva o binário cru e responde em 8 ms, antes de qualquer processamento:

```json
{ "status": 202, "id": 5 }
```

A consulta de andamento responde um dos quatro valores do enum do frontend, e nada além disso:

```json
{ "status": 200, "video_status": "Finalizado", "motivo": null }
```

E o resultado traz uma linha por etapa, na ordem em que o grafo as executou:

```json
{
  "status": 200,
  "video_status": "Finalizado",
  "resultados": [
    { "nome_processo": "ball", "status": true, "frame": null, "metricas": [] },
    { "nome_processo": "field", "status": true, "frame": null, "metricas": [] },
    { "nome_processo": "players", "status": true, "frame": null, "metricas": [] },
    { "nome_processo": "shot", "status": true, "frame": null, "metricas": [] },
    { "nome_processo": "identity", "status": true, "frame": null, "metricas": [] },
    { "nome_processo": "pose", "status": true, "frame": null, "metricas": [] },
    { "nome_processo": "tracking", "status": true, "frame": null, "metricas": [] }
  ],
  "motivo": null
}
```

Duas coisas nesse corpo vêm vazias hoje, e vêm vazias de propósito. `metricas` só é preenchida na
etapa `shot`, e só quando existe feature declarada: o `config/pipeline.toml` que vai para produção
não tem nenhuma seção `[features.*]`, então em toda execução real a lista sai vazia. `frame` é a
imagem de demonstração e responde `null` porque a visualização não entra nesta sprint.

A tradução para métrica existe e é exercitada. Com duas features declaradas numa cópia da
configuração, uma que mede e outra que não consegue, a mesma rota devolve:

```json
{
  "nome_processo": "shot",
  "status": true,
  "frame": null,
  "metricas": [
    { "nome": "distancia_falsa", "unidade_de_medida": "m", "tipo": "float", "valor": 11.5, "status": "ok" },
    { "nome": "sem_leitura", "unidade_de_medida": "m", "tipo": "float", "valor": null, "status": "unavailable" }
  ]
}
```

O campo `status` da métrica existe para que número medido e número indisponível não cheguem à tela
com a mesma cara. A unidade vem da `FeatureSpec` de cada feature, e não de um sufixo no nome: quem
sabe a unidade é a feature, e derivar metro de um `_m` quebraria na primeira que não seguisse a
convenção.

### As rotas, e o que cada uma declara

Os códigos abaixo saem do `src/api/docs/openapi.json`, que é gerado pelo próprio app e conferido
por teste contra o código:

| Rota | Sucesso | Recusas declaradas |
| --- | --- | --- |
| `GET /` | 200 | nenhuma |
| `GET /health` | 200 | nenhuma |
| `POST /v1/auth/register` | 201 | 409, 422 |
| `POST /v1/auth/login` | 200 | 401, 422 |
| `GET /v1/auth/me` | 200 | 401 |
| `POST /v1/videos/upload-url` | 200 | 401, 415, 422 |
| `PUT /v1/videos/upload/{token}` | 202 | 400, 404, 409, 413, 415, 422, 503 |
| `POST /v1/videos/processamento` | 202 | 400, 401, 413, 415, 422, 503 |
| `GET /v1/videos/status/{video_id}` | 200 | 401, 404, 422 |
| `GET /v1/videos/{video_id}` | 200 | 401, 404, 409, 422 |

O 422 aparece em toda rota que valida corpo ou caminho: é o que o pydantic devolve. O serviço
registra um tratador próprio para ele porque a resposta padrão embute o corpo recebido dentro do
erro, e o corpo aqui é um vídeo inteiro. O tratador remove o campo `input` e converte o que não
serializa, então a recusa de validação sai em dezenas de bytes em vez de devolver o envio de
volta: medido hoje, um corpo de 7,0 MB sem o campo `contentType` recebe 83 bytes de resposta.

Declarar a recusa não é enfeite de documentação: o FastAPI só descreve no contrato o que a rota
declara, e um cliente gerado a partir do arquivo trata como sucesso qualquer código que não esteja
lá. Um teste provoca cada recusa de verdade, batendo na rota, e falha se o serviço responder um
código que o contrato não declara.

## Decisões

**O processamento é assíncrono, e a rota de envio responde 202.** Quem envia recebe o
identificador na hora e consulta depois. *Alternativa descartada:* devolver o resultado na mesma
requisição, que foi a primeira versão. Ela amarra a duração do pipeline à duração de uma conexão
HTTP, e obriga o corpo inteiro a existir em memória. É preciso separar o que é fato do que é
projeção: com os módulos de percepção ainda em stub, a fixture sintética atravessa o pipeline em
14 ms no melhor caso e 81 ms no pior (13 execuções medidas hoje, mediana de 38 ms). O clipe que
leva segundos é o clipe com modelo de verdade sobre vídeo de partida, e esse número ainda não
existe. A decisão é para o segundo caso, e ela custa pouco no primeiro.

**Existem dois caminhos de envio porque chegaram duas especificações.** A mensagem do contrato
escrito pede o vídeo em base64 dentro do JSON, e é essa que o código do frontend em
`src/interface` implementa hoje: `useVideoUpload.ts` converte o arquivo com `fileToBase64` e
`videoService.ts` posta o par de campos `file` e `type` em `/videos/processamento`. A outra
especificação, a de pedir uma URL e mandar o binário cru por `PUT` no desenho de uma URL
pré-assinada, ainda não tem cliente escrito. O campo de tipo aparece ora como `contentType`, ora
como `type`, e o serviço aceita os dois nomes. *Alternativa descartada:* escolher uma das
especificações e descobrir a divergência no dia da integração. Custa um alias e uma rota, e não
custa uma reunião. O caminho recomendado continua sendo o `PUT`, porque o corpo é transmitido por
pedaço direto para o disco: medido hoje, um envio de 100 MB por `PUT` manteve o RSS do processo
entre 66,1 MB e 66,6 MB do começo ao fim da transmissão. O base64 tem teto próprio de 32 MB contra
128 MB do `PUT`, porque a codificação produz 4 bytes de saída para cada 3 de entrada e o texto
inteiro precisa existir em memória antes de virar bytes.

**O endereço de envio aponta para o próprio serviço, no formato de uma URL pré-assinada.** Ele é
um token opaco de 32 bytes sorteados, vale uma vez só e está preso a um vídeo. *Alternativa
descartada:* exigir também o cabeçalho `Authorization` no `PUT`, que não fecharia nada e custaria
alcance, pelo argumento que está em [autenticação e posse do vídeo](/docs/sprint-2/backend/autenticacao).
A posse do endereço sai de um `UPDATE` condicional, e não de ler o estado e depois gravar: medido
no serviço anterior, dois `PUT` no mesmo endereço passavam os dois, e com a fila ocupada isso
acontecia sempre, mesmo sem simultaneidade, porque a janela era a fila inteira. Trocar este serviço
por um armazenamento de objetos no dia da implantação muda apenas quem escreve o endereço, e não o
frontend.

**Um middleware recusa corpo grande pelo cabeçalho, antes de ele existir em memória.** Medido
hoje: um `POST` no caminho base64 declarando `Content-Length` de 300 MB foi recusado com 413 em
0,8 ms, sem que o cliente chegasse a transmitir um byte de corpo, e o RSS do processo não se mexeu
do começo ao fim, 29,0 MB nos dois lados. *Alternativa descartada:* conferir o tamanho depois que
o pydantic materializa a string, que protege a metade menor do problema: medido no serviço
anterior e registrado no teste que hoje guarda o middleware, um `POST` de 300 MB devolvia o 413
correto e levava o processo de 65 MB para 1176 MB de RSS. Numa borda de 2 GB isso é falta de
memória com dois clientes, e a resposta certa não ajuda em nada.

**O teto por pedaço é a segunda linha, para o caso em que não há cabeçalho.** Envio fragmentado
não declara `Content-Length`, e aí não há o que conferir antes. Medido hoje: um `PUT` de 200 MB
com `Content-Length` foi cortado em 5 ms, antes de o cliente conseguir transmitir corpo nenhum;
o mesmo `PUT` sem `Content-Length` só foi cortado depois de 137.965.432 bytes recebidos. As duas
mensagens são diferentes de propósito, `o corpo passa do teto de 128 MB` contra `o video passa do
teto de 128 MB`, e é assim que se sabe qual das duas linhas recusou. *Alternativa descartada:*
recusar de saída todo envio sem `Content-Length`, o que fecharia a porta para quem transmite sem
saber o tamanho final e ainda deixaria a proteção inteira apoiada num cabeçalho que o cliente
escreve.

**A fila é de um worker por padrão.** *Alternativa descartada:* deixar o pool de threads do
Starlette decidir, que aceita quarenta chamadas bloqueantes ao mesmo tempo. Cada pipeline abre o
próprio decodificador, e memória é o recurso escasso num dispositivo de borda: medido no serviço
síncrono anterior, três envios simultâneos de 300 MB levaram o processo a 2,81 GB de pico. Uma
fila de um troca pico de memória por espera na fila, que é a troca certa aqui, porque latência de
fila não é o recurso escasso. O número sai de `XVISION_API_WORKERS` para quem tiver máquina folgada.

**Fila cheia responde 503 com `Retry-After`, e não aceita o trabalho.** Medido hoje, com o teto de
fila em 2 e doze envios simultâneos: 2 aceitos com 202, 10 recusados com 503, todos com
`retry-after: 30`. *Alternativa descartada:* aceitar tudo, que foi o comportamento anterior:
medido, 200 envios foram aceitos em 0,28 s e chegaram a 186 arquivos simultâneos em `var/uploads`,
sem nada devolver recusa. Aceitar trabalho que não se consegue fazer é pior que recusá-lo, porque
quem chamou fica esperando um resultado que nunca vem. O código é 503 e não 429 porque 429 diz que
o chamador excedeu a própria cota, e aqui não há cota por chamador: o que falta é capacidade do
serviço, que é exatamente o que o 503 significa.

**O estado mora em SQLite, em `var/api/jobs.db`.** Quem envia o vídeo e quem pergunta pelo
resultado são duas requisições diferentes, e entre elas não há memória confiável: o processo pode
reiniciar e o worker roda em outra thread. *Alternativa descartada:* PostgreSQL, que resolveria o
mesmo problema cobrando um serviço, um contêiner e uma credencial que a necessidade presente não
justifica. O modo de journal é WAL, que é o que deixa a requisição de consulta ler enquanto o
worker escreve, e cada operação abre a própria conexão, o que dispensa compartilhar conexão entre
threads. O gatilho da troca está nomeado nos trade-offs.

**O esquema é versionado por `PRAGMA user_version`.** As migrações são uma tupla de comandos em
que o índice é a versão, e a subida aplica só o que falta. Medido: um banco recém-criado sai com
`user_version` igual a 3, que é o tamanho da tupla, e `journal_mode` igual a `wal`. *Alternativa
descartada:* `CREATE TABLE IF NOT EXISTS` sozinho, que cria banco novo e não conserta banco velho,
de modo que a coluna nova faltaria em produção e nunca no teste de quem a escreveu. *Alternativa
descartada:* Alembic, que traz SQLAlchemy junto, e aqui não há ORM nem chamador que escreva SQL:
seriam duas dependências para versionar uma tabela. A regra que fecha o desenho é que migração já
aplicada nunca é editada, só acrescentada, porque editar uma deixa dois bancos com o mesmo
`user_version` e esquemas diferentes.

**As transições válidas são declaradas, e sair de um estado terminal é erro.** São exatamente os
quatro estados do enum do frontend, sem um quinto:

| De | Para onde pode ir |
| --- | --- |
| `Pendente` | `Em processamento`, `Falhou` |
| `Em processamento` | `Em processamento`, `Finalizado`, `Falhou` |
| `Finalizado` | lugar nenhum |
| `Falhou` | lugar nenhum |

*Alternativa descartada:* validar apenas se o valor está na lista de estados, que deixa passar o
que importa. Medido no serviço anterior: dois envios no mesmo endereço faziam um lado marcar
`Falhou` e o worker do outro gravar `Finalizado` por cima, e o registro terminava contando a
história errada. A transição de `Em processamento` para ele mesmo é permitida de propósito, porque
é o que a recuperação de queda faz ao retomar um vídeo que já estava nesse estado.

**Queda no meio do trabalho é recuperada na subida seguinte.** O que separa um trabalho
interrompido de um endereço de envio que o cliente ainda não usou é a posse, e não o estado: um
vídeo que já tinha os bytes e esperava a vez continua em `Pendente`, e precisa voltar do mesmo
jeito. Se o arquivo enviado sobreviveu, o clipe é refeito; se não sobrou, o vídeo vai para
`Falhou` com motivo, porque fingir `Pendente` deixaria o frontend consultando para sempre.
*Alternativa descartada:* a versão anterior, que só trocava a coluna para `Pendente` e não
reenfileirava nada, de modo que o frontend passava a girar em `Pendente` em vez de girar em
`Em processamento`. Fila cheia durante a recuperação para a rodada e não derruba a subida: sem
isso, um número de órfãos maior que o teto faria o serviço não subir nunca mais, porque os órfãos
continuam lá.

**O contrato mora sob `/v1`, e `/health` fica fora dele.** O prefixo vem de um `APIRouter`, não
repetido em cada caminho, então publicar a `v2` é criar um router novo e manter o antigo
respondendo. *Alternativa descartada:* versionar por cabeçalho, que não funciona aqui porque o
endereço de envio é entregue pronto ao cliente e precisa carregar a versão dentro dele. Rota de
operação fica fora da versão porque um orquestrador que consulta saúde não deveria precisar saber
em que versão o contrato está. Chamada sem versão é o erro mais provável de quem integra, e a raiz
responde para onde ir:

```json
{ "servico": "xVision", "versoes": ["/v1"], "atual": "/v1", "docs": "/docs", "openapi": "/openapi.json" }
```

**O serviço recusa a subir com configuração quebrada.** Medido hoje: sem `XVISION_AUTH_SECRET` a
subida falha dizendo que o serviço não assina sessão sem ela, e com `XVISION_API_MAX_UPLOAD_MB` no
valor `128MB`, com o sufixo a mais, a subida falha dizendo que aquilo não é um número de
megabytes. *Alternativa descartada:* ler a configuração por requisição, dentro do worker, que foi
o comportamento anterior: o erro de digitação passava por toda sonda de prontidão, `/health`
respondia ok, e o primeiro envio morria como 500.

**Toda rota de negócio exige credencial, e vídeo de outro responde 404.** A regra, o desenho das
duas credenciais e o motivo de o 403 ter sido descartado estão em
[autenticação e posse do vídeo](/docs/sprint-2/backend/autenticacao); o que interessa aqui é o
efeito no contrato. As rotas que consultam declaram 401 e 404, e nenhuma declara 403, então um
cliente gerado a partir do arquivo não tem como distinguir vídeo de outro de vídeo inexistente. A
única rota de vídeo fora dessa exigência é o `PUT` do endereço de envio, porque o próprio endereço
já é a credencial. Fora dela, só a raiz, o `/health`, o registro e o login respondem sem
`Authorization`, e os dois últimos existem justamente para quem ainda não tem credencial.

### De onde vêm os números desta página

Três origens, e elas não se misturam. Os números marcados como medidos hoje vêm de uma execução
do serviço em `uvicorn`, nesta máquina, com `curl` e amostragem de RSS por `ps` a cada 30 ms; são
reproduzíveis e valem para este hardware, não para a Jetson. Os números marcados como medidos no
serviço anterior vêm das docstrings e dos testes que guardam cada correção, e descrevem um código
que não existe mais: eles justificam a decisão, e não descrevem o comportamento atual. O que não
tem medição está escrito como projeção. A suíte da API tem 162 testes e cobre 97,68% das linhas
de `src/api`; nesta máquina, três execuções de `pytest src/tests/api` levaram entre 9,0 s e
12,2 s, e 11,3 s com a medição de cobertura ligada.

## Trade-offs

**A desvantagem principal do assíncrono é que o frontend precisa perguntar.** Não há notificação,
nem campo de progresso, nem posição na fila: a tela mostra `Em processamento` por um tempo que ela
não sabe estimar. Enquanto o pipeline leva dezenas de milissegundos isso é invisível, e com modelo
de verdade passa a ser a principal queixa de quem usa.

**A desvantagem da fila de um é a vazão.** Um clipe por vez, e com o teto de 32 na fila o último a
ser aceito espera os 31 que já estavam nela. A troca é deliberada, porque o pico de memória é o
que derruba um dispositivo de borda e a espera não é, mas ela existe e aparece no primeiro uso
com várias pessoas ao mesmo tempo.

**A desvantagem principal do SQLite é que um arquivo não se replica.** No dia em que o serviço
rodar em mais de uma instância, isto vira PostgreSQL. A troca fica contida porque nenhum chamador
conhece SQL, só as funções de `store.py`, mas ela vai acontecer, e o gatilho é a segunda instância.

**A desvantagem dos dois caminhos de envio é manter e testar duas superfícies.** Ela se paga
enquanto as duas especificações estiverem em aberto, e deve ser cobrada quando o time do frontend
fechar em uma.

**A desvantagem do 413 pelo cabeçalho é que `Content-Length` é afirmação do cliente.** Ele some em
envio fragmentado, e aí quem segura é o teto por pedaço, que só corta depois de ter recebido os
bytes: medido, 132 MB entraram antes do corte. A proteção barata cobre o caso comum, e o caso
incomum custa banda.

**A desvantagem da triagem de tipo pela porta é que a prova real vem depois do upload.** Qualquer
`video/*` passa na porta, e quem decide é o decodificador, que abre o arquivo já gravado. Medido
hoje: 100 MB que não eram vídeo foram recebidos inteiros em 0,22 s e só então recusados com 415.
Evitar isso exigiria conferir assinatura nos primeiros bytes durante a transmissão, o que
resolveria o arquivo obviamente inválido e não o vídeo corrompido no meio, que é o caso que mais
aparece.

**A desvantagem do 404 no lugar do 403 recai sobre o usuário honesto.** Quem tem acesso legítimo e
erra o identificador recebe a mesma resposta de quem está sondando, e não descobre que o vídeo
existe.

## Riscos e incertezas

**O tempo real do pipeline é desconhecido, e dois parâmetros dependem dele.** O teto de 32 na fila
e o `Retry-After` de 30 s foram escolhidos sem esse número. Se um clipe de partida levar minutos,
30 s manda o cliente voltar cedo demais e a fila de 32 vira meia hora de espera aceita em
silêncio; se levar menos de um segundo, os dois valores são conservadores à toa.

**A fila é de um processo, e não existe fila entre máquinas.** Se o processo morre, os vídeos em
voo voltam na subida seguinte, e há teste para os dois casos. O que não há é coordenação: duas
instâncias sobre o mesmo `var/` recuperariam os mesmos órfãos e processariam o mesmo vídeo duas
vezes.

**Não há limite de taxa por chamador.** O teto de corpo e o teto de fila seguram volume, não
frequência. Um cliente em laço não derruba o serviço, mas ocupa a fila inteira e empurra todos os
outros para o 503.

**O disco em trânsito não tem teto próprio.** O arquivo enviado fica em `var/uploads/` entre o 202
e o fim do processamento, e com o teto de fila em 32 e 128 MB por arquivo o pior caso é da ordem
de 4 GB. Esse número é estimativa por multiplicação, não medição: ninguém encheu a fila com
arquivos no tamanho máximo.

**A configuração de CORS falha em silêncio.** O padrão libera as origens de desenvolvimento, e
esquecer de ajustar `XVISION_CORS_ORIGINS` na implantação faz o navegador do usuário bloquear a
chamada sem que o serviço registre nada de anormal.

**O cliente do frontend ainda não fecha com este contrato, em três pontos.** O `api.ts` de
`src/interface` não manda cabeçalho `Authorization` em chamada nenhuma, e as duas rotas que ele
usa exigem credencial, então a integração de hoje responderia 401 antes de qualquer vídeo entrar.
Ele lê o resultado em `/videos_processados/{id}`, endereço que este serviço não publica, porque o
resultado sai em `GET /v1/videos/{video_id}`. E os nomes de campo declarados em `videoService.ts`
não são os que o serviço devolve: no nível do resultado, `results` contra `resultados`, `name`
contra `nome_processo` e `metrics` contra `metricas`; dentro de cada métrica, `name`,
`unit_measurement`, `type` e `value` contra `nome`, `unidade_de_medida`, `tipo` e `valor`, que
ainda ganha o `status` que o tipo do frontend não prevê. Nenhum dos três é difícil de resolver, e
os três dependem de uma decisão conjunta sobre qual lado muda.

## Referências

- [RFC 9110, HTTP Semantics](https://datatracker.ietf.org/doc/html/rfc9110), que define 202, 413, 503 e o cabeçalho `Retry-After`, os quatro elementos com que este serviço enfileira, recusa corpo e recusa capacidade.
- [RFC 6585, Additional HTTP Status Codes](https://datatracker.ietf.org/doc/html/rfc6585), que define 429 como excesso de requisições do chamador e sustenta a escolha de responder 503, e não 429, quando a fila enche.
- [FastAPI, Additional Responses in OpenAPI](https://fastapi.tiangolo.com/advanced/additional-responses/), que descreve como uma rota declara os códigos que devolve e por que o contrato gerado só documenta o que foi declarado, razão de cada recusa desta página estar na tabela de rotas.
- [Starlette, Requests](https://www.starlette.io/requests/), cuja API de fluxo do corpo é o que permite gravar o envio por pedaço em vez de materializá-lo, e sustenta a medição do envio de 100 MB sem crescimento de RSS.
- [SQLite, appropriate uses](https://www.sqlite.org/whentouse.html), que é o critério usado para escolher SQLite agora e o gatilho declarado para trocar por um banco cliente-servidor depois.
- [SQLite, PRAGMA user_version](https://www.sqlite.org/pragma.html#pragma_user_version), o inteiro guardado dentro do arquivo que aqui conta quantas migrações já rodaram.
- [SQLite, Write-Ahead Logging](https://www.sqlite.org/wal.html), que sustenta o `journal_mode=WAL` e a leitura concorrente com a escrita do worker.
- [RFC 4648, The Base16, Base32, and Base64 Data Encodings](https://datatracker.ietf.org/doc/html/rfc4648), que descreve a expansão de 3 bytes de entrada para 4 de saída, razão do teto menor no caminho base64.
- [Amazon S3, presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html), o desenho que o endereço de envio imita para que trocar por armazenamento de objetos não mexa no frontend.
- [Documentação de `concurrent.futures`](https://docs.python.org/3/library/concurrent.futures.html), base do pool de um worker e do desligamento que cancela o que ainda não começou.
- [Documentação de `secrets`](https://docs.python.org/3/library/secrets.html), gerador do token de 32 bytes que autoriza gravar os bytes do vídeo uma única vez.
