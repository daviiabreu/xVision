description: Processamento assíncrono, o envio em duas etapas, a fila de um worker e o estado que sobrevive a uma queda
---

O serviço HTTP é a ponte entre o navegador e [a borda](/docs/sprint-2/backend/borda), e a área
`api` da [visão geral do backend](/docs/sprint-2/backend): ele aceita o vídeo, enfileira o
processamento e devolve o resultado por etapa. Na arquitetura de destino essa ponte cruza a rede,
e nesta sprint as duas pontas rodam na mesma máquina.

## Onde se encaixa no fluxo

```text
navegador                    serviço HTTP (src/api)                borda (src/edge)
    │                               │                                    │
    │ POST /v1/videos/upload-url    │                                    │
    ├──────────────────────────────►│ store.criar: id + token de 32 B    │
    │◄──────────────────────────────┤                                    │
    │                               │                                    │
    │ PUT uploadUrl, binário cru    │                                    │
    ├──────────────────────────────►│ middleware confere Content-Length  │
    │                               │ grava por pedaço em var/uploads/   │
    │                               │ probe() abre o cabeçalho do vídeo  │
    │◄── 202 {"status":202,"id":5} ─┤ execution.submeter ► fila de 1 ────► process_clip
    │                               │                                    │
    │ GET /v1/videos/status/5       │                                    │
    ├──────────────────────────────►│ lê var/api/jobs.db                 │
    │◄─ "Em processamento" ─────────┤◄─── store.marcar(Finalizado) ──────┤
    │                               │                                    │
    │ GET /v1/videos/5              │                                    │
    ├──────────────────────────────►│ uma linha por etapa do pipeline    │
    │◄──────────────────────────────┤                                    │
```

O serviço é área de composição, como o `cli`: ele importa `edge` e ninguém o importa de volta.
Essa direção é cobrada por teste, e não confiada à disciplina.

## Componentes e responsabilidades

| Componente | Responsabilidade | O que ele **não** faz |
| --- | --- | --- |
| `api/__init__.py` | rotas, middlewares, ciclo de vida e a tabela de códigos que cada rota declara | não roda pipeline, não escreve SQL e não decide o que é uma feature |
| `api/schemas.py` | a forma do que entra e do que sai, e a regra de tipo de cada métrica | não escolhe status HTTP, não toca no banco e não monta o resultado: quem preenche é `execution.py` |
| `api/store.py` | o estado dos vídeos e das contas, em SQLite, com a máquina de estados dentro | não conhece HTTP e não decide o que fazer com um vídeo interrompido |
| `api/execution.py` | rodar o pipeline fora do ciclo da requisição, com teto de fila, e traduzir o evento da borda em uma linha por etapa | não deixa exceção subir, não sabe quem chamou e não impõe prazo ao desligamento: ele cancela o que não começou e espera o clipe em voo |
| `api/seguranca.py` | traduzir o cabeçalho `Authorization` em `Principal` e cobrar a [posse do vídeo](/docs/sprint-2/backend/autenticacao) | não emite credencial e não guarda segredo |
| `api/auth.py` | assinar sessão, conferir senha com `scrypt` e resumir token de serviço | não fala HTTP e não lê o banco |
| `api/render.py` | resolver os pesos do manifesto e chamar o desenho da visão superior por clipe | não desenha nada: quem desenha é `src/models/top_view/create_top_view.py`, e peça que falta vira motivo, não exceção |
| `api/export.py` | escrever `src/api/docs/openapi.json` a partir do app que roda | não edita o contrato à mão |

A fronteira mais importante é a de `store.py`: ele lê os vídeos que uma queda deixou pelo meio e
não faz nada com eles. Quem sabe reprocessar é a camada que tem a fila, então a decisão mora em
quem pode submeter, e não em quem sabe consultar.

## Fluxo de dados

Entra um clipe de vídeo e sai uma lista de etapas do pipeline, uma linha por módulo de percepção.
O que segue é a troca real, capturada contra o serviço rodando sobre a fixture sintética do
repositório (3 s, 30 quadros, 320 por 240, 25 KB), com os identificadores como saíram.

O frontend pede um endereço de envio:

```json
{ "fileName": "synthetic.mp4", "contentType": "video/mp4" }
```

E recebe o identificador e o endereço, já com a versão dentro:

```json
{ "id": 5, "uploadUrl": "/v1/videos/upload/gjhFiaaIccwFyLBkPXPq..." }
```

O `PUT` naquele endereço leva o binário cru e responde em 2 ms, antes de qualquer processamento:

```json
{ "status": 202, "id": 5 }
```

A consulta de andamento responde um dos quatro valores do enum do frontend, e nada além disso:

```json
{ "status": 200, "video_status": "Finalizado", "motivo": null }
```

E o resultado traz uma linha por etapa, na ordem em que o grafo as executou:

```json
{
  "status": 200,
  "video_status": "Finalizado",
  "resultados": [
    { "nome_processo": "ball", "status": true, "frame": null, "metricas": [] },
    { "nome_processo": "field", "status": true, "frame": null, "metricas": [] },
    { "nome_processo": "identity", "status": true, "frame": null, "metricas": [] },
    { "nome_processo": "players", "status": true, "frame": null, "metricas": [] },
    { "nome_processo": "pose", "status": true, "frame": null, "metricas": [] },
    { "nome_processo": "tracking", "status": true, "frame": null, "metricas": [] },
    {
      "nome_processo": "shot",
      "status": true,
      "frame": null,
      "metricas": [
        { "nome": "body_part", "unidade_de_medida": "classe", "tipo": null, "valor": null, "status": "unavailable" },
        { "nome": "type_of_play", "unidade_de_medida": "classe", "tipo": "text", "valor": "individual", "status": "ok" }
      ]
    }
  ],
  "motivo": null,
  "render_url": "/v1/videos/5/render"
}
```

`metricas` só é preenchida na etapa `shot`, que é a que ancora o instante do contato, e o
`config/pipeline.toml` que vai para produção declara duas features: `[features.body_part]` e
`[features.type_of_play]`. A lista deixou de sair vazia, e o que ela traz precisa ser lido com
cuidado, porque declarada e medida não são a mesma coisa. Nesta execução `type_of_play` respondeu
`individual` com `status: "ok"` e `body_part` respondeu `unavailable`, e nenhum dos dois valores é
inferência: o `pipeline.toml` roda seis das sete espécies em stub, e stub responde a partir do
gabarito da fixture e nunca dos pixels. O número que sai de modelo exige o
`config/pipeline.models.toml`, que troca `players`, `ball`, `tracking` e `pose` pelas
implementações reais e depende dos pesos em `var/models`. Quais espécies e quais métricas existem
de cada lado está em [o que fica para a próxima sprint](/docs/sprint-2/o-que-falta). `frame` continua `null`,
e por outro motivo: é a imagem de demonstração, e a visualização não entra nesta sprint.

A tradução de feature em métrica é exercitada nos três casos que importam. O
`src/tests/api/test_metricas.py` acrescenta, a uma cópia da configuração de produção, uma feature
que mede um número, uma que não consegue medir e uma que mede uma categoria. As duas features
reais vêm junto, porque a cópia parte de onde elas já estão declaradas, e a mesma rota devolve
cinco métricas na etapa `shot`:

```json
{
  "nome_processo": "shot",
  "status": true,
  "frame": null,
  "metricas": [
    { "nome": "body_part", "unidade_de_medida": "classe", "tipo": null, "valor": null, "status": "unavailable" },
    { "nome": "type_of_play", "unidade_de_medida": "classe", "tipo": "text", "valor": "individual", "status": "ok" },
    { "nome": "distancia_falsa", "unidade_de_medida": "m", "tipo": "float", "valor": 11.5, "status": "ok" },
    { "nome": "sem_leitura", "unidade_de_medida": "m", "tipo": null, "valor": null, "status": "unavailable" },
    { "nome": "parte_do_corpo", "unidade_de_medida": "", "tipo": "text", "valor": "PERNA_ESQUERDA", "status": "ok" }
  ]
}
```

O campo `tipo` tem três valores, `boolean`, `float` e `text`, e sai do valor que a feature
devolveu, não de uma declaração da `FeatureSpec`. Texto é o caso das features categóricas, e três
dos onze blocos `[[label]]` de `config/labels.toml` declaram `type = "enum"`: `body_part_2`,
`body_part_3` e `type_of_play`. A fronteira apagava o valor textual e mandava `valor: null` ao lado de
`status: "ok"`, duas afirmações que se contradizem, e a tela lia a primeira e escrevia
`indisponível` para uma medida que deu certo.

A consequência de o tipo sair do valor é que sem valor não há tipo, e o campo é nulo nesse caso.
O `else` que existia antes respondia `float` para toda leitura ausente, e para as duas features
`enum` acima isso é afirmar número onde nunca vai haver número. Nulo é a única resposta que não
inventa nada, e a tela não lê o campo para decidir o que desenhar: `Metric.tsx` decide pelo tipo
do valor que chegou, o que mantém as duas pontas de acordo sem precisar confiar no campo.

O campo `status` da métrica existe para que número medido e número indisponível não cheguem à tela
com a mesma cara. A unidade vem da `FeatureSpec` de cada feature, e não de um sufixo no nome: quem
sabe a unidade é a feature, e derivar metro de um `_m` quebraria na primeira que não seguisse a
convenção.

### As rotas e o que cada uma declara

Os códigos abaixo saem do `src/api/docs/openapi.json`, que é gerado pelo próprio app e conferido
por teste contra o código:

| Rota | Sucesso | Recusas declaradas |
| --- | --- | --- |
| `GET /` | 200 | nenhuma |
| `GET /health` | 200 | nenhuma |
| `POST /v1/auth/register` | 201 | 409, 422, 429 |
| `POST /v1/auth/login` | 200 | 401, 422, 429 |
| `GET /v1/auth/me` | 200 | 401 |
| `POST /v1/videos/upload-url` | 200 | 401, 415, 422 |
| `PUT /v1/videos/upload/{token}` | 202 | 400, 404, 409, 413, 415, 422, 503 |
| `GET /v1/videos/status/{video_id}` | 200 | 401, 404, 422 |
| `GET /v1/videos/{video_id}` | 200 | 401, 404, 409, 422 |
| `GET /v1/videos/{video_id}/render` | 200 | 401, 404, 422 |

O 422 aparece em toda rota que valida corpo ou caminho: é o que o pydantic devolve. O serviço
registra um tratador próprio para ele porque a resposta padrão embute o corpo recebido dentro do
erro. O tratador remove o campo `input` e converte o que não serializa, então a recusa de
validação sai em dezenas de bytes em vez de devolver o envio de volta: medido no serviço anterior,
quando existia a rota que aceitava o vídeo em base64 dentro do JSON, um corpo de 7,0 MB sem o campo
`contentType` recebeu 83 bytes de resposta. Hoje nenhuma rota carrega o vídeo no corpo que o
pydantic valida, e o tratador fica porque não custa nada, vale para todo corpo recusado, e a
próxima rota com corpo grande não vai lembrar de pedi-lo.

Declarar a recusa não é enfeite de documentação: o FastAPI só descreve no contrato o que a rota
declara, e um cliente gerado a partir do arquivo trata como sucesso qualquer código que não esteja
lá. Um teste provoca cada recusa de verdade, batendo na rota, e falha se o serviço responder um
código que o contrato não declara.

### O vídeo anotado que a interface mostra

Até aqui o resultado era só número, e enquanto a percepção inteira era stub ele era número nenhum:
a tela dizia que a análise tinha rodado e não mostrava nada. O serviço passa a produzir, por
clipe, o vídeo da visão superior, com o quadro anotado à esquerda e a posição projetada no gramado
à direita, e a interface o exibe acima das métricas.

Quem desenha é `src/models/top_view/create_top_view.py`, que já existia. O `src/api/render.py`
importa `process_video` e chama, em vez de reimplementar o desenho, e assim existe uma implementação
só: mudança no desenho aparece na tela sem ninguém copiar nada. Três coisas ficam do lado do
serviço, porque um script de operador não precisa delas e um serviço não funciona sem: o peso vem do
manifesto declarado em `[render.top_view]`, com sha256 conferido, em vez de um caminho relativo ao
diretório de quem treinou; o arquivo termina em `var/api/renders`, porque `src/` é área de código e
o serviço só escreve em `var/`; e falta de peça vira motivo registrado em vez de exceção, porque
ilustração ausente não é falha de análise. É por isso que `render_url` nem sempre vem preenchido: os
dois pesos de `[render.top_view]` são material derivado de dado restrito e não estão no git, e num
clone sem `var/models` o serviço levanta `RenderUnavailable` com `o peso de players nao esta
pronto`, registra `sem visao superior` no log, devolve `render_url` nulo e conclui a análise assim
mesmo.

O render não depende do desfecho da análise, e isso foi medido antes de ser decidido: num clipe
real de partida com o `config/pipeline.toml` padrão, em que a bola é stub e responde pelo gabarito
da fixture, a espécie `shot` não aponta instante de contato, `process_clip` levanta
`NoShotDetected` e o vídeo terminava em `Falhou` sem nada na tela. Agora clipe que não abre
continua sendo recusa do arquivo, e falha de pipeline vira `Falhou` com motivo e com o vídeo
gravado do mesmo jeito. A tela mostra os dois: o motivo e o vídeo.

O custo é assimétrico e é o principal preço desta escolha. Medido num clipe da Footstats de 4 s a
59,94 fps, 240 quadros, em CPU: 2 s de análise contra 84 s de render, porque o script roda dois
modelos em cada quadro do clipe, e não nos quadros que o conjunto declarado escolhe. O vídeo sai
com 4,5 MB em H.264, que é o formato que navegador toca.

## Referências

- [RFC 9110, HTTP Semantics](https://datatracker.ietf.org/doc/html/rfc9110), que define 202, 413, 503 e o cabeçalho `Retry-After`, os quatro elementos com que este serviço enfileira, recusa corpo e recusa capacidade.
- [RFC 6585, Additional HTTP Status Codes](https://datatracker.ietf.org/doc/html/rfc6585), que define 429 como excesso de requisições do chamador e sustenta a escolha de responder 503, e não 429, quando a fila enche.
- [FastAPI, Additional Responses in OpenAPI](https://fastapi.tiangolo.com/advanced/additional-responses/), que descreve como uma rota declara os códigos que devolve e por que o contrato gerado só documenta o que foi declarado, razão de cada recusa desta página estar na tabela de rotas.
- [Starlette, Requests](https://www.starlette.io/requests/), cuja API de fluxo do corpo é o que permite gravar o envio por pedaço em vez de materializá-lo, e sustenta a medição do envio de 100 MB sem crescimento de RSS.
- [SQLite, appropriate uses](https://www.sqlite.org/whentouse.html), que é o critério usado para escolher SQLite agora e o gatilho declarado para trocar por um banco cliente-servidor depois.
- [SQLite, PRAGMA user_version](https://www.sqlite.org/pragma.html#pragma_user_version), o inteiro guardado dentro do arquivo que aqui conta quantas migrações já rodaram.
- [SQLite, Write-Ahead Logging](https://www.sqlite.org/wal.html), que sustenta o `journal_mode=WAL` e a leitura concorrente com a escrita do worker.
- [RFC 4648, The Base16, Base32, and Base64 Data Encodings](https://datatracker.ietf.org/doc/html/rfc4648), que descreve a expansão de 3 bytes de entrada para 4 de saída, os 33% que justificam a retirada do caminho base64 e o teto menor que ele teve enquanto existiu.
- [Amazon S3, presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html), o desenho que o endereço de envio imita para que trocar por armazenamento de objetos não mexa no frontend.
- [Documentação de `concurrent.futures`](https://docs.python.org/3/library/concurrent.futures.html), base do pool de um worker e do desligamento que cancela o que ainda não começou.
- [Documentação de `secrets`](https://docs.python.org/3/library/secrets.html), gerador do token de 32 bytes que autoriza gravar os bytes do vídeo uma única vez.
